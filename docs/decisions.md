| 2026-11-27 | application-service enforces "one application per scholarship" and "max 3 active" with one DynamoDB `TransactWriteItems` per apply: the application + a lock row `lock#one#<student>#<scholarship>` + an active-slot lock row `lock#slot#<student>#<1-3>`, each with a condition. Lock rows live in `Applications` (no new table) with only `applicationId`, `lockType`, `holder`, `createdAt`, so they are not in any index. A slot frees itself when its holder is accepted/rejected/gone (checked inside the transaction); withdraw releases both locks in the same transaction. Any Scan of `Applications` must filter `attribute_exists(studentId)`. Applications created before this change have no lock rows: delete the `Applications` table once (`aws dynamodb delete-table --table-name Applications --profile floci`) and run application-service `deploy.sh` again (`platform/reset.sh` is still a TODO). | Reading first and writing after let two requests at the same moment both pass (shown by `tests/concurrency-tests.js` on the old code: both got 201). | 2026-11-27 | Scholarship rules in admin-service: `criterionId` is a slug set by the admin (`academic`, unique per rubric); deadlines must be a full ISO 8601 date-time with a zone (past allowed on a draft, future required to publish); eligibility `years` are whole numbers 1-6.
